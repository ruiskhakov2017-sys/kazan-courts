# Decision log — решения Homework 004

Исходные решения ниже восстановлены по уточнению пользователя и являются пересказом обсуждения, а не дословными цитатами или обязательно самыми первыми гипотезами до критики AI. Более ранние формулировки, не подтверждённые источниками, не восстанавливаются. Планируемое не является фактом реализации.

## 1. Погода и ошибка провайдера

- **Реконструкция решения пользователя:** недоступность Open-Meteo — техническая проблема, а не хорошая погода; при ухудшении бронь остаётся активной, при улучшении формируется второе уведомление.
- **AI challenge:** `unknown` нельзя считать хорошей погодой; технический сбой не должен стирать дождевой запрет.
- **Итоговое решение пользователя:** оператор видит техническое предупреждение и последнее успешное время, восстановление снимает предупреждение, ошибка не снимает дождевые предупреждения, выход за горизонт не является техническим сбоем.
- **Trade-off:** требуется постоянный статус и отдельная классификация; stale данные не равны актуальному прогнозу.

## 2. Kafka и атомарность

- **Реконструкция решения пользователя:** Kafka передаёт погодные события отдельному обработчику клиентских уведомлений; Transactional Outbox включается как сознательное учебное решение.
- **AI challenge:** запись БД и отправка брокеру раздельно могут потерять событие; повтор после сбоя создаёт дубли.
- **Итоговое решение пользователя:** один broker/topic, два погодных типа события, обязательный transactional outbox с отдельным publisher, отдельный consumer для имитации, таблицы `OutboxMessage` и `SimulatedNotification`.
- **Trade-off:** дополнительные процессы и миграции; at-least-once требует дедупликации и обработки устаревших сообщений. Детали контракта — [kafka-design.md](kafka-design.md).

## 3. Покрытие и погода

- **Реконструкция решения пользователя:** физическая готовность и погодный запрет — независимые состояния; после осмотра сотрудник может подтвердить готовность даже при blocked.
- **AI challenge:** подтверждение покрытия не должно разрешать бронь в дождевом блоке.
- **Итоговое решение пользователя:** разрешить `drying` → `available` после осмотра; запрет на создание/перенос в blocked остаётся отдельным.
- **Trade-off:** два независимых состояния требуют понятного отображения оператору и отдельных проверок.

## 4. Автоматическая проверка и повторы

- **Реконструкция решения пользователя:** две категории относительно порога 72 часа; перенос или отмену выполняет оператор после связи с клиентом.
- **AI challenge:** временные ошибки требуют ограниченных повторов; бесконечный retry и ложный clear опасны.
- **Итоговое решение пользователя:** почасовой запуск и до трёх попыток при временных ошибках; 72 часа — порог разделения очередей оператора.
- **Уточнение пользователя для этапа 3:** timeout 5 секунд, максимум три попытки и паузы 1 и 3 секунды; `Retry-After` соблюдается, длительное ожидание откладывает следующую автоматическую попытку.
- **Trade-off:** предупреждения могут задерживаться до следующего цикла; дополнительные запросы увеличивают нагрузку.

## 5. Очередь сотрудника и повтор запроса

- **Решение пользователя:** единое серверное время, две очереди вокруг порога 72 часа; «Не дозвонились» не изменяет бронь, а намеренная повторная попытка должна быть отдельным действием.
- **AI challenge:** потерянный ответ или повторная отправка способны создать вторую запись, даже если первая транзакция уже завершилась.
- **Итоговое решение:** идентификатор запроса хранится в снимке события и в `sessionStorage` вкладки; при повторе того же запроса возвращается существующее событие. Новая подтверждённая попытка получает другой идентификатор. Проверка и запись сериализуются блокировкой брони.
- **Trade-off:** без новой таблицы не гарантируется автоматическое восстановление идентификатора в другой вкладке или после окончания её сеанса; браузер не отправляет действие, если не может сохранить идентификатор.

## 6. Проверка Kafka в CI

- **Решение пользователя:** временный Kafka 4.2.2 на GitHub runner, явное подтверждение двух integration-тестов и Node для четырёх JS-тестов.
- **AI challenge:** для job на host адрес `kafka:9092` недоступен, а зелёный набор может скрыть пропущенные Kafka-тесты.
- **Итоговое решение:** broker сообщает `127.0.0.1:9092`, topic с одной partition проверяется клиентом runner; результаты обоих тестов явно контролируются. Фактическая проверка GitHub workflow ожидает разрешённых commit и PR.
- **Trade-off:** дополнительный broker увеличивает время и расход ресурсов CI; отдельная GitHub-проверка ещё не подтверждена.
