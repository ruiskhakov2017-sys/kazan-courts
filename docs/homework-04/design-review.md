# Design review — Draft / Planned

## Подтверждённые границы

Существующий Django объединяет API и операции бронирования; PostgreSQL хранит состояние и `BookingEvent`, а погодный адаптер и правила находятся в отдельных модулях. Конкретные функции и транзакции — [current-system-map.md](current-system-map.md). Это логические ответственности; из их наличия не следует необходимость отдельных сервисов.

## Утверждённое решение пользователя

Для Homework 004 добавить почасовую проверку, три таблицы `WeatherIntegrationStatus`, `OutboxMessage`, `SimulatedNotification`, расширить `BookingEvent`, использовать один Kafka topic, publisher и consumer-имитатор. Новые механизмы ещё не реализованы.

## AI challenge и предложение

Граница сетевого вызова и транзакции важнее изменения структуры каталогов: ошибка между записью брони и отправкой в Kafka создаёт риск потери события. Согласованный outbox связывает переход и сообщение в PostgreSQL; отдельный publisher допускает повтор, поэтому consumer должен быть идемпотентным. Trade-off: больше таблиц и процессов при малом учебном объёме, зато сбои и границы ответственности можно проверить.

Одно небольшое предложение AI: при реализации выделить функции автоматической классификации и переходов погоды в отдельный модуль рядом с `weather_client.py`, сохранив публичные вызовы и `BookingEvent`. Сейчас перенос файлов не выполняется; группировка — предложение для review, не утверждённый рефакторинг.

## Риски и проверка

Гонка переноса/отмены требует перечитывать бронь под блокировкой; задержанное сообщение может быть устаревшим; уникальность event ID предотвращает дубликат результата, но не обеспечивает порядок. Интеграционные и failure-сценарии перечислены в [kafka-design.md](kafka-design.md); они пока не выполнены. Реальные уведомления и дополнительные инфраструктурные компоненты вне scope.
