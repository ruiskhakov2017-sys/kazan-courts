# Reliability decisions — Draft / Planned

## Исходные данные и решения

Исходная самостоятельная retry-policy пользователя в доступных материалах не зафиксирована. Утверждено: до трёх попыток Open-Meteo при временных ошибках; оператор видит техническую проблему и время последнего успешного автоматического запроса; после восстановления предупреждение исчезает. Вне горизонта — не технический сбой.

Факт: [`fetch_forecast()`](../../bookings/weather_client.py) сейчас делает одну попытку, timeout 5 секунд, при ошибке возвращает unavailable; реальных повторов пока нет. Текущий ручной recheck может заменить blocked на unknown; будущая политика должна это исправить.

## Предложение AI: retry, timeout и rate limits

Предлагается сохранить timeout 5 секунд на попытку, максимум три попытки всего, с паузами **1 и 3 секунды**; эти интервалы и конкретный timeout для будущего scheduler ожидают review, не являются отдельно утверждёнными значениями. Повторять timeout/сетевую временную ошибку, 429 и временный 5xx; ограничивать частоту общим почасовым запуском, не делать бесконечные повторы. Обработка `Retry-After`, лимит его ожидания и окончательная классификация 4xx/некорректного ответа требуют уточнения перед реализацией; тестами подтвердить отсутствие шторма запросов. Не сохранять секреты, PII и полные ошибки провайдера.

## Ошибки, данные и heartbeat

| Случай | Planned поведение |
|---|---|
| Провайдер недоступен после повторов | `WeatherIntegrationStatus`: время автоматической попытки, безопасный код, счётчик; предупредить оператора. Не менять blocked на clear. |
| Частичный/некорректный ответ | Не считать неполные часы хорошей погодой и не снимать blocked; определить безопасную классификацию и не называть частичный ответ полным успехом без проверки контракта. |
| Бронь вне полученного горизонта | Не выводить техническую неисправность из-за самой даты; не менять её на clear. |
| Успех после сбоя | Обновить время последнего успешного автоматического прогноза, сбросить ошибку и убрать техническое предупреждение. |
| Scheduler не включён / ещё не запускался | Отдельное начальное состояние, без ложной аварии. Ручная проверка не обновляет автоматический heartbeat. |

Согласно плану, просроченность — отсутствие успеха более двух часовых циклов после начала работы scheduler; конкретная семантика первого запуска и границы требует теста. Статус хранится в одной записи PostgreSQL; при недоступности PostgreSQL записать новую ошибку невозможно, а старый успех становится просроченным при следующем доступном чтении.

## Проверки и ограничения

Planned: mock timeout → success, 429/5xx → успех, исчерпание, невалидный и частичный ответ, восстановление, просроченный heartbeat, отсутствие первого запуска, ручной запрос, выход за горизонт и сохранение blocked. Внешний Open-Meteo — только по отдельному разрешению; локальные тесты используют фальш-ответы. Фактические результаты будут в `testing-report.md` на этапе 6.
