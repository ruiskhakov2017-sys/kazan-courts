# Reliability decisions — Draft / Planned

## Исходные данные и решения

Исходная самостоятельная retry-policy пользователя в доступных материалах не зафиксирована. Утверждено: до трёх попыток Open-Meteo при временных ошибках; оператор видит техническую проблему и время последнего успешного автоматического запроса; после восстановления предупреждение исчезает. Вне горизонта — не технический сбой.

На этапе 3 ручной [`fetch_forecast()`](../../bookings/weather_client.py) по-прежнему делает одну попытку. Отдельная автоматическая функция выполняет ограниченные повторы. Ручной recheck сохраняет прежний `blocked` при неизвестном прогнозе. Реальные запросы в проверках этапа 3 не выполнялись.

## Предложение AI: retry, timeout и rate limits

Пользователь утвердил timeout 5 секунд на попытку, максимум три попытки всего и паузы **1 и 3 секунды**. Автоматическая проверка повторяет временные сетевые ошибки, HTTP 429 и 500/502/503/504; постоянные 4xx и структурно некорректный ответ не повторяются. Если `Retry-After` превышает очередную допустимую паузу, проверка завершается с технической ошибкой и сохраняет время следующей автоматической попытки в PostgreSQL. Учебная политика: корректные отсрочки до семи суток соблюдаются полностью, включая 48 часов; неправдоподобные более длинные ограничиваются семью сутками, некорректные — одним часом. В обоих случаях пишется безопасное предупреждение в журнал без исходного значения заголовка, а оператор видит техническую ошибку интеграции. Для значения более семи суток возможен повтор раньше указанного сервером срока; это явный компромисс ограничения. На этапе 4 добавлен почасовой процесс, который при отключённом сетевом доступе ожидает и не создаёт ложного сбоя. Не сохранять секреты, PII и полные ошибки провайдера.

Структурно корректный ответ может содержать пропуски, `null` и погодные коды, не относящиеся к согласованным дождевым и бездождевым: они дают `unknown` только для соответствующих блоков. Известный дождь в блоке имеет приоритет; правила снега и грозы не расширяются. Время последнего успеха отражает получение структурно корректного ответа провайдера, включая частичный ответ, а не завершение обработки всех броней. Если последующая обработка падает, команда завершается ошибкой и не выводит `status=success`; её успешное выполнение не сохраняется как отдельный статус цикла. Операторский индикатор явно ограничивает значение последнего успеха получением прогноза.

## Ошибки, данные и heartbeat

| Случай | Planned поведение |
|---|---|
| Провайдер недоступен после повторов | `WeatherIntegrationStatus`: время автоматической попытки, безопасный код, счётчик; предупредить оператора. Не менять blocked на clear. |
| Частичный/некорректный ответ | Не считать неполные часы хорошей погодой и не снимать blocked; определить безопасную классификацию и не называть частичный ответ полным успехом без проверки контракта. |
| Бронь вне полученного горизонта | Не выводить техническую неисправность из-за самой даты; не менять её на clear. |
| Успех после сбоя | Обновить время последнего успешного автоматического прогноза, сбросить ошибку и убрать техническое предупреждение. |
| Scheduler не включён / ещё не запускался | Отдельное начальное состояние, без ложной аварии. Ручная проверка не обновляет автоматический heartbeat. |

Согласно плану, просроченность — отсутствие успеха более двух часовых циклов после начала работы scheduler; конкретная семантика первого запуска и границы требует теста. Статус хранится в одной записи PostgreSQL; при недоступности PostgreSQL записать новую ошибку невозможно, а старый успех становится просроченным при следующем доступном чтении.

## Проверки и ограничения

Этап 3: автоматические тесты с фальш-ответами покрывают повторы, исчерпание, отложенный `Retry-After`, невалидный и частичный ответ, восстановление и сохранение blocked при ручной перепроверке. Внешний Open-Meteo не вызывался; проверка реального провайдера требует отдельного разрешения. Итоговый отчёт всех этапов остаётся на этапе 6.
