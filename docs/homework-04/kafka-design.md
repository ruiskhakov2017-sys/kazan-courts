# Kafka design — Draft / Planned

## Решения и назначение

Пользователь согласовал одну Apache Kafka с одним topic и событиями `booking.weather_blocked` / `booking.weather_cleared`, transactional outbox, отдельные publisher и consumer-имитатор, один локальный broker. Kafka — учебное требование ментора; для небольшого MVP возможна более простая схема. Факт исходного кода: компонентов Kafka и outbox ещё нет; исходная цепочка — [current-system-map.md](current-system-map.md).

## Components and event contract

Один topic, две разновидности событий; ключ сообщения `booking_id`, неизменный `event_id` — ключ идемпотентности. **Предложение AI для review:** JSON envelope `event_id`, `event_type`, `schema_version`, `booking_id`, `court_id`, `occurred_at`, `episode_id`; `episode_id` связывает ухудшение с последующим улучшением. Имена topic, точный формат версии, сериализация и детали эпизода подлежат окончательной проверке на этапе реализации. Данные контактов и другие клиентские PII в Kafka не включаются.

## Background flow

Planned: scheduler раз в час получает прогноз вне транзакции, повторно проверяет бронь → PostgreSQL атомарно сохраняет изменение, `BookingEvent` и `OutboxMessage` → publisher передаёт запись в Kafka → consumer проверяет актуальность и сохраняет `SimulatedNotification` (`SIMULATED` или `SUPPRESSED`). Consumer ничего не отправляет клиенту. Подробнее — [system-sequences.md](system-sequences.md).

## Outbox proposal

Уникальный `event_id`, тип/версия, payload, создание, публикация, количество попыток и безопасный код ошибки хранятся в PostgreSQL. Publisher отмечает запись опубликованной только после подтверждения брокера. Точная стратегия конкурентного выбора записей и сохранения порядка между повторными публикациями — открытый технический вопрос этапа 4; никакой глобальный порядок не обещается.

## Delivery guarantees

Цель — at-least-once доставка при сохранении outbox и повторной работе процессов, а не exactly-once между PostgreSQL и Kafka. Consumer записывает результат с уникальностью `event_id` в транзакции и подтверждает offset после commit БД. Повтор доставки одного `event_id` не создаёт вторую имитацию. Ключ `booking_id` позволяет маршрутизировать события одной брони в одну partition при стабильной конфигурации; сам по себе ключ не исправляет перестановку публикаций. Consumer должен подавлять отменённые и устаревшие события после проверки актуального состояния/эпизода; точный механизм проверки предстоит подтвердить тестами.

## Failure modes

| Сбой | Ожидаемый механизм и проверка |
|---|---|
| Откат PostgreSQL | Ни изменение, ни история, ни outbox не остаются. |
| Kafka недоступна | Outbox остаётся ожидающим; после восстановления publisher повторяет. |
| Брокер подтвердил, publisher упал до отметки | Возможен дубль с тем же `event_id`; consumer дедуплицирует. |
| БД consumer committed, offset не подтверждён | Повтор безопасен по уникальному `event_id`. |
| Событие устарело или бронь отменена | Фиксируется `SUPPRESSED`; имитация отправки не выполняется. |

Проверить на реальных локальных PostgreSQL и Kafka, включая повторы, остановку/восстановление, конкуренцию и порядок; пока это план, не результаты тестов. Дополнительные topics, DLQ, Debezium и настоящая рассылка вне согласованного scope.
