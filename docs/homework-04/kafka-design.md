# Kafka design — реализация этапа 4 объединена в main

Пользователь утвердил один локальный брокер, один topic, Transactional Outbox и отдельный имитатор уведомлений. В Compose используется Apache Kafka 4.2.2, topic `booking.weather.v1` с одной partition; Python 3.14.8 и `kafka-python==3.0.12`. Kafka и PostgreSQL имеют разные volumes. Порт Kafka наружу не опубликован. Это учебная конфигурация, не отказоустойчивый кластер.

## Контракт и цепочка

События `booking.weather_blocked` и `booking.weather_cleared` содержат JSON: `event_id`, `event_type`, `schema_version=1`, `booking_id`, `court_id`, `occurred_at`, `episode_id` (может быть null для исторических броней). Ключ Kafka — `booking_id`; телефонов, имён и других клиентских PII в сообщении нет. Переход, BookingEvent и Outbox сохраняются вместе в PostgreSQL; Kafka не входит в эту транзакцию.

`publish_pending()` берёт PostgreSQL session advisory lock, обрабатывает ожидающие записи по id и ждёт подтверждения broker через `send().get()` с `acks=all`. Только затем сохраняется `published_at`. Ошибки непригодного payload помечаются `invalid_payload`, ошибки Kafka — `kafka_unavailable`, прочие ошибки отправки — `publisher_error`; содержимое сообщения и секреты не включаются в журнал. На первой ошибке запись остаётся ожидающей; следующие не пропускаются и задерживаются. После подтверждения и до отметки возможна повторная публикация того же `event_id`. Один брокер и одна реплика означают, что `acks=all` не обеспечивает сохранность при потере диска брокера. Для порядка предполагается один активный publisher; при потере PostgreSQL-сессии одновременно с сетевой операцией lock уже не защищает от перекрытия процессов.

Consumer сверяет envelope с сохранённой записью Outbox, блокирует бронь и в транзакции создаёт единственный `SimulatedNotification` на `event_id`. Актуально только событие действующей будущей неархивированной брони открытого корта с соответствующим текущим погодным статусом, если после события нет нового `weather_blocked`, `weather_cleared`, `rescheduled`, `cancelled`, `archived` или изменившей статус ручной проверки `weather_checked`. История проверяется по идентификатору события, а не только nullable `episode_id`. Непосредственно следующая запись сотрудника, чьи снимки подтверждают тот же системный переход, считается аудитом этого перехода; проверка без изменения статуса также не делает событие устаревшим. Недостаточные снимки трактуются консервативно как устаревание. Контакт «Не дозвонились» не делает событие устаревшим.

Записывается `simulated` или `suppressed`; настоящих сообщений нет. Offset конкретной записи подтверждается после успешного выхода из транзакции PostgreSQL. Повтор после записи в БД до подтверждения offset возвращает прежний результат, не создавая новый. Некорректный или отсутствующий в Outbox event не подтверждается: обработка останавливается на нём и периодически повторяется. Так как partition одна, последующие сообщения всех броней тоже не обрабатываются; повтор без устранения причины не восстанавливает очередь. Нужны проверка журналов и отдельное решение об исправлении данных или обработке сообщения; автоматический пропуск, ручное подтверждение offset и DLQ не реализованы. Дубли возможны, поэтому обещается at-least-once, а не exactly-once.

## Scheduler и отказ

Отдельный процесс вызывает прежнюю однократную проверку сразу при старте и затем примерно раз в час. При временных ошибках сети/провайдера или PostgreSQL допускаются три коротких повтора через 60, 120 и 300 секунд, затем часовая пауза; после успеха счётчик сбрасывается. Каждый повтор — отдельный цикл с прежним максимумом трёх HTTP-попыток. Постоянный HTTP 4xx и некорректный ответ не получают коротких повторов. Сохранённый `Retry-After` имеет приоритет: scheduler может просыпаться не реже раза в час для проверки состояния, но запрос до `next_allowed_at` запрещён PostgreSQL-проверкой. Счётчик коротких повторов хранится только в памяти и сбрасывается при перезапуске процесса; сам `Retry-After` сохраняется в БД. При `WEATHER_NETWORK_ENABLED=0` scheduler простаивает, не обращается к Open-Meteo и не создаёт ложную техническую ошибку. При недоступности Kafka Outbox остаётся в PostgreSQL, publisher повторяет попытку после восстановления; consumer возобновляет чтение с последнего подтверждённого offset.
