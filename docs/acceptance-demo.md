## 1. Подготовка

1. Использовать учебные данные: семь синтетических кортов и три вымышленных клиента.
   Существующие записи и историю не очищать перед показом.
2. Подготовить Docker Desktop и окружение PowerShell по [README](../README.md):
   секреты вводятся скрыто или восстанавливаются локально без печати значений.
   Обычный web доступен на http://127.0.0.1:8000/.
3. Для новой пустой среды выполнить миграции, seed и создание сотрудника по README.
   В уже подготовленной базе использовать существующего сотрудника; его пароль
   и права не сбрасывать. Перед миграциями подтвердить имя development-базы и роль.
4. Для основного сценария взять крытый корт и завтрашний день по Казани.
   Проверить свободные промежутки. Начало и конец — с шагом 10 минут,
   минимум час; весь интервал должен закончиться не позднее текущего времени
   плюс один календарный месяц по Казани. Пример свободного времени:
   13:20–14:20 и 15:20–16:20; если занято, выбрать другие подходящие интервалы.
5. Реальную погодную сеть оставить выключенной. Дождь показывается подготовленными
   тестами; настоящий Open-Meteo в этой демонстрации не вызывается.

После подготовки переменных окружения доступны штатные команды README:

```powershell
docker compose up --build -d --wait --wait-timeout 120
if ($LASTEXITCODE -ne 0) { throw "Compose не готов к демонстрации." }
docker compose ps
docker compose exec web python manage.py check
if ($LASTEXITCODE -ne 0) { throw "Django check не прошёл." }
docker compose exec web python manage.py migrate --check
if ($LASTEXITCODE -ne 0) { throw "Остались неприменённые миграции." }
```

При ошибке подготовки сначала разобрать фактическую причину.
Не удалять volume и не сбрасывать базу ради продолжения показа.

## 2. Показ в браузере — примерно 10 минут

| Шаг | Действие | Что должен увидеть принимающий |
|---|---|---|
| 1. Вход | Открыть / без сессии, затем войти сотрудником | Перенаправление на login; после входа семь кортов, три клиента |
| 2. Расписание | Выбрать крытый корт и завтрашний день | Записи и свободные промежутки по Казани; свободный промежуток не обещает окончательного разрешения |
| 3. Создание | Клиент с телефоном, свободный интервал от часа | Номер сохранённой брони, запись в расписании, событие создания |
| 4. Конфликт | Попытаться создать другую бронь в том же интервале | Понятный отказ; исходная бронь и история сохранены, второй записи нет |
| 5. Неверное время | Ввести отдельный интервал длительностью 30 минут | Ошибка у конца; запись не создаётся, значения сохраняются |
| 6. Перенос | Открыть исходную бронь, выбрать другое свободное время, указать вымышленную причину | Новое время и событие переноса; клиент и корт сохранены |
| 7. Отмена | Причина, подтверждающий флажок, отмена | Время освободилось; «Показать отменённые» возвращает запись в список |
| 8. История | Открыть историю отменённой записи | Создание → перенос → отмена, сотрудник, причины и изменения; физического удаления нет |
| 9. Погода | Выбрать открытый корт | Четыре периода по 6 часов и предупреждение unknown при выключенной сети |
| 10. Покрытие | На готовом демонстрационном открытом корте закрыть на просушку, затем подтвердить после проверки | drying → available; физическая готовность и погодное предупреждение показаны отдельно |
| 11. Выход | Нажать «Выйти», снова открыть / | Сессия завершена, требуется вход |

Открытая бронь с unknown может быть показана дополнительно, если завтрашний
интервал находится в сезоне `[1 мая 00:00, 1 ноября 00:00)` и остальные условия
выполнены. Вне сезона демонстрировать отказ и пояснение, не менять часы сервера.
Подтверждение физической готовности при показе проверяет действие в учебной
системе, а не удостоверяет осмотр реального клуба.

После показа учебные записи и история остаются в БД. При необходимости отменить
действующие демонстрационные брони штатной операцией до их начала; физически не удалять.
Архивирование реализовано через API, отдельной кнопки экрана нет:
его сохранность доказывает test_booking_actions, а не несуществующее действие UI.

## 3. Доказательства БД и конкуренции

Показать SQL-проверку development identity из README:
`current_database()` = kazan_courts_dev, `current_user` = kazan_dev.
Затем показать [testing-report](testing-report.md) и успешный CI.
Если принимающий хочет новый прогон, выполнить блок изолированных тестов README:
сначала запустить db и дождаться healthy; DB_NAME=postgres,
DB_USER=kazan_test, тестовый пароль из локального окружения, сеть выключена.
Не запускать два runner одновременно на одном сервере с общим именем test database.

Ожидаемый результат:

- полный набор: 145 тестов, OK;
- Django сам создаёт и удаляет test_kazan_courts;
- после прогона test database отсутствует, development существует,
  CONNECT у kazan_test к development остаётся false;
- отдельный повтор трёх concurrency-модулей: 11 тестов, OK;
- конфликтующие запросы на независимых PID оставляют одну бронь и событие;
  смежные запросы допускаются, ожидания Court/Booking действительно проверяются.

Архив, атомарный откат истории, CSRF, запреты доступа и ошибка БД покрыты тестами.
Дождевые коды, blocked, unknown и независимость покрытия от погодного запрета
показываются тестами test_weather_policy / test_weather_operations.
Тестовые подстановки не меняют обычный web; прогноз за текущую дату в сети не нужен.

## 4. Что объяснить своими словами

1. Почему SELECT «свободно» недостаточен и как PostgreSQL exclusion constraint
   защищает INSERT/UPDATE при конкуренции; почему смежные интервалы разрешены.
2. Где заканчивается погодный вызов и начинается короткая atomic;
   почему Booking и BookingEvent сохраняются вместе.
3. Чем отличаются Court FOR SHARE, ручное FOR NO KEY UPDATE и Booking FOR UPDATE.
4. Как разные роли и запрет CONNECT отделяют тесты от development.
5. Почему unknown не означает сухую погоду, а available не снимает blocked.
6. Почему потерянный ответ POST не означает rollback и не повторяется автоматически.
7. Почему очереди/worker пока не нужны и какие гарантии не обещает текущая версия.

Ссылки для объяснения: [design](design.md), [decision-log](decision-log.md),
[level3-notes](level3-notes.md). Исходные гипотезы, которых пользователь не
формулировал, не представлять как его самостоятельные решения.
