# 2. Технические решения и архитектура учебного сервиса

**Назначение:** техническая карта решений, согласованных при подготовке: из каких частей состоит сервис, кто за что отвечает, как устроены данные и что должно гарантировать отсутствие двойной брони. Этот файл нужен пользователю для осознанных решений, Codex — для анализа узких задач, ментору — для архитектурного review.

**Состояние:** документ описывает согласованную целевую архитектуру; фактическая граница транзакции создания брони на этапе 05 уточнена в разделе 5. Реализованный объём и результаты проверок фиксируются в `docs/testing-report.md`. Конкретный код, имена Python-модулей и состав отдельных миграций Codex предлагает в плане задачи и не меняет без разрешения пользователя.

## 1. Исходная архитектурная гипотеза пользователя

При нажатии «Забронировать» пользователь сам описал путь: **фронтенд → бэкенд → база данных → бэкенд → фронтенд**. Позже он уточнил приоритеты: сам принимает проектные решения, избегает искусственных задержек, требует понятных ответов и использует Codex как исполнителя после согласования плана. Отдельного исходного `design.md` до работы с AI не существовало; схема ниже возникла в ходе обсуждения.

AI дополнительно показал риск одновременных проверок «время свободно» и сравнил блокировку строки целого корта с ограничением PostgreSQL по пересекающимся интервалам. Пользователь выбрал второй механизм; он не хотел заставлять бронирование вторника ждать бронирование понедельника без необходимости.

## 2. Выбранные технологии и роль каждой

| Часть | Решение | Зачем |
|---|---|---|
| Серверный язык | **Python** | Бизнес-правила, обработка запросов и погодного ответа |
| Серверное приложение | **Django** | Страницы, авторизация одного сотрудника, действия с бронированиями |
| Фронтенд | **Django Templates + обычный JavaScript** | Django готовит HTML, браузер показывает страницы и отправляет действия; отдельного React-приложения нет |
| Программа хранения данных | **PostgreSQL** | Единственный источник истины для клиентов, кортов, броней и истории |
| Работа Django с базой | **Django ORM** для обычных действий | Чтение и запись через Python; особое ограничение пересечений остаётся на уровне PostgreSQL |
| API | **Небольшой JSON API средствами Django** | Страница запрашивает корты, доступность, создаёт и меняет бронь; Django REST Framework пока не нужен |
| Погода | **Open-Meteo** | Почасовой прогноз для открытых кортов |
| Проверки | **Встроенные тесты Django**, отдельно — настоящая тестовая PostgreSQL | Проверить правила, API, транзакции и одновременные запросы |
| Локальный запуск | **Docker Compose, когда понадобится совместный запуск Django и PostgreSQL** | Воспроизводимая среда; Compose обязателен к завершению Homework, но не первая самоцель |
| Карта — расширение | **Яндекс Карты** | Семь синтетических маркеров в Казани |
| Почта — расширение | **Django SMTP через отдельный учебный ящик Яндекс Почты** | Настоящая отправка подтверждений email и уведомлений |

Никаких дополнительных Redis, Celery, очередей, фоновых исполнителей, отдельного frontend-сервера, `AGENTS.md` и пользовательских skills заранее не создаём. Их появление возможно только при конкретно обоснованной необходимости и отдельном решении пользователя.

## 3. Как взаимодействуют части

```text
Браузер сотрудника
  (Django Templates + JavaScript)
            │ запрос / ответ HTML или JSON
            ▼
Django на Python
  ├── вход одного сотрудника
  ├── проверка правил бронирования
  ├── погодная проверка ────► Open-Meteo
  └── короткая операция записи
            │
            ▼
PostgreSQL
  (корты, клиенты, брони, события истории,
   окончательный запрет пересечений)
```

Браузер работает на устройстве пользователя, поэтому для него не нужен контейнер. Если применён Docker Compose, в нём достаточно сервисов Django и PostgreSQL. Django Templates — часть самого Django, а не отдельный сервер.

**Граница доверия:** интерфейс может показать свободное время, но окончательное разрешение на бронь принимает сервер при работе с PostgreSQL. Пользователь мог открыть две вкладки; между отображением и нажатием ситуация могла измениться.

## 4. Модель данных

**Court — корт.** Идентификатор, название, крытый/открытый тип, синтетические координаты Казани, состояние покрытия (`available`, `drying`, `maintenance`) и отметка последней проверки. Всего семь демонстрационных записей. Сезонность — правило для типа корта, а не отдельный список из сотен дат.

**Customer — клиент.** Идентификатор, имя, обязательный телефон, необязательный email. В первой версии это запись о клиенте, **не аккаунт для входа**. Создадим несколько вымышленных клиентов, чтобы брони были связаны с разными людьми.

**Booking — бронь.** Идентификатор, ссылка на корт, ссылка на клиента, начало и конец, состояние (`active`/`cancelled`), причина отмены при наличии, необязательная отметка архива, время создания/изменения, ссылка на сотрудника, который оформил бронь. Архивирование не удаляет запись. Только действующие брони занимают время.

**BookingEvent — история действий.** Для каждой операции: какая бронь, кто и когда её изменил, тип действия (создание, перенос, отмена, архивация), прежние и новые значения и причина при наличии. Это технический способ исполнить требование пользователя «все брони остаются и можно выяснить, что произошло». Изменение брони и событие истории должны сохраняться вместе.

**Сотрудник.** Одна стандартная учётная запись Django с логином `admin`, доступ ко всем кортам. Специальная таблица Staff и сложные роли не нужны; статус технического Django-superuser для решения бизнес-задачи не обязателен. Простой выбранный учебный пароль устанавливается локально, не записывается в код, документы или Git; до любого внешнего доступа он должен быть заменён.

**Связи:** одна запись Court имеет множество Booking; одна Customer имеет множество Booking; одна Booking имеет множество BookingEvent. Несуществующего клиента или корта нельзя связать с бронью.

## 5. Гарантия от двойной брони

Для каждого действующего бронирования используются интервалы **[начало, конец)**: начало включено, конец исключён. Поэтому 14:00–16:00 и 16:00–17:00 не пересекаются. Время хранится однозначно с часовым поясом, а на экране показывается по Казани.

**Принятое решение:** Django заранее проверяет время, сезон, погоду и доступность и объясняет отказы. PostgreSQL содержит **exclusion constraint** — правило, запрещающее двум действующим броням одного корта иметь пересекающиеся интервалы. Состояние отменённых броней исключается из этого запрета, поэтому отмена освобождает время, но запись остаётся. Конкретный синтаксис миграции, подходящий тип временного диапазона и необходимые расширения PostgreSQL Codex должен предъявить в плане и сверить с фактической версией БД перед применением.

**Короткая транзакция (transaction)** охватывает запись/перенос/отмену брони и соответствующего BookingEvent. Если при переносе возник конфликт, вся операция откатывается: прежнее время и корректная история остаются. Не держим транзакцию открытой в ожидании ответа Open-Meteo. Реально пересекающиеся одновременные запросы могут кратко ждать решения базы, но бронирования одного корта на разные дни мы не ставим искусственно в одну очередь блокировкой строки Court.

### Фактическая граница транзакции создания — этап 05

В текущем POST `/api/bookings/` обработчик `bookings/api.py` проверяет вход,
допуск сотрудника, HTTP-метод, Content-Type, JSON и форму до вызова сервиса.
Штатная CSRF-проверка Django также выполняется до сервисной транзакции.
Транзакция не охватывает весь HTTP-запрос; `ATOMIC_REQUESTS` не включён.

В `bookings/services.py` функция `create_booking` открывает один
`transaction.atomic()`. Внутри него последовательно выполняются:

1. Чтение актуальной учётной записи активного сотрудника, существующих клиента
   и корта; проверка телефона клиента.
2. Получение одного серверного `now` и проверки будущего времени, обеих
   десятиминутных границ, минимальной длительности, календарного месяца и сезона.
3. Предварительная проверка пересечения с действующими бронями.
4. Запись активной Booking с серверным автором и одного BookingEvent(created):
   `before=None`, `after` — снимок сохранённой брони, `actor` — сотрудник.

И чтения, и проверки правил находятся внутри этой короткой транзакции;
её граница не ограничена только двумя INSERT. В ней нет внешних сетевых
вызовов или общей блокировки строки Court. Предварительная проверка не устраняет
гонку: окончательный запрет пересечения обеспечивает PostgreSQL constraint
`booking_active_no_overlap`.

`IntegrityError` обрабатывается после выхода из `atomic`, когда неудачная
операция уже откатилась. Только SQLSTATE `23P01` с именем этого ограничения
преобразуется в `time_conflict` / HTTP 409; остальные ошибки БД не выдаются
за конфликт времени. Ошибка записи истории также откатывает запись брони.
В обычном HTTP-запросе сервис возвращает результат после успешного завершения
транзакции, и лишь затем обработчик формирует HTTP 201.

Эта граница описывает реализованное создание. Операции этапа 06 описаны ниже;
погода и ручное состояние покрытия — этап 07; сетевой запрос Open-Meteo
по согласованному принципу должен оставаться вне транзакции записи.
Правила операции и обязательная история обеспечиваются через сервис;
прямой ORM/SQL его обходит, триггеры истории на этапе 05 не добавлены.

**Пользовательское поведение при конфликте:** Django возвращает контролируемый ответ о занятом интервале, а интерфейс предлагает обновить свободное время. Сырые сообщения SQL на экран не попадают.

### Фактическая граница изменения — этап 06

Серверные reschedule_booking, cancel_booking и archive_booking используют
общую короткую транзакцию `_booking_transaction`. HTTP-метод, JSON, форма
и CSRF проверяются до вызова сервиса. Внутри atomic проверяется актуальный
допуск сотрудника и блокируется только изменяемая Booking через
`select_for_update().get(...)`, без JOIN и блокировки Court.

Серверный now определяется после получения блокировки. Перенос и отмена
допустимы только для ещё не начавшейся действующей неархивированной брони.
Перенос меняет только время и повторяет проверки клиента с телефоном, корта,
нового интервала, календарного месяца и сезона. Precheck исключает собственную
Booking; окончательное ограничение пересечений остаётся в PostgreSQL.

Снимок before снимается с заблокированной актуальной строки. Затем сохраняются
только поля действия и updated_at, записывается одно событие с after, actor,
reason и occurred_at, равным updated_at брони. created_by/created_at,
клиент и корт сохраняются. Ошибка записи любого элемента откатывает всю операцию;
IntegrityError преобразуется после выхода из atomic по правилу этапа 05.
HTTP 200 возвращается после успешного завершения транзакции.

Создание и три действия обёрнуты в `_retry_deadlock`: только при OperationalError
с исходным PostgreSQL SQLSTATE 40P01 выполняется один повтор всей операции.
Исключение перехватывается после выхода из atomic и отката неуспешной попытки.
В HTTP-сценарии внешней транзакции нет; новая попытка заново проверяет сотрудника,
читает/блокирует Booking, определяет now и проверяет данные. Максимум две попытки;
повторный deadlock и остальные ошибки БД сохраняют общий HTTP 503. Ошибка 23P01
не повторяется, а преобразуется в конфликт по прежнему правилу. Повтор отдельного
SQL-запроса внутри сломанной транзакции не применяется.

Отмена освобождает время без удаления; архивировать можно любую отменённую
неархивированную запись, будущую или прошлую. Повторные отмена/архив дают 409,
перенос на прежний интервал — 400; события успешного действия не дублируются.
Причина необязательна. Старые события не переписываются, физического удаления
через сервис/API нет. Прямой SQL/ORM владельца БД по-прежнему обходит сервис.

GET /api/bookings/ показывает пересекающие выбранные сутки действующие и
отменённые записи без архива. GET /api/bookings/<id>/history/ доступен сотруднику
и после архивации; события упорядочены по occurred_at, затем ID.
Расписание по-прежнему показывает только действующие записи.

## 6. Правила времени, доступности и погоды

Сервер проверяет будущее время, максимум один календарный месяц вперёд, шаг в 10 минут, длительность не менее часа; крытые корты работают круглый год, открытые — только 1 мая–31 октября. Новое время при переносе проходит те же проверки. Расчёты времени и шестичасовые блоки интерфейс показывает в часовом поясе Казани.

Погодный адаптер получает из Open-Meteo почасовые данные и переводит их в понятные признаки: «дождь/морось», «без дождя», «прогноз недоступен». Конкретные поля ответа проверяются по документации перед программированием; продуктовый порог уже принят: **осадки в любом часу блока запрещают весь блок открытых кортов**. При недоступном прогнозе разрешено оформление с видимым предупреждением и пометкой для ручной перепроверки. Автоматической очереди пока нет. После фактического дождя сотрудник вручную подтверждает готовность покрытия.

## 7. Функциональный API-контракт

API (Application Programming Interface) — способ для страницы попросить Django выполнить действие и получить структурированный ответ. Для нашего масштаба достаточно обычных обработчиков Django, которые возвращают JSON. До начала программирования Codex покажет конкретные URL и поля; **формат URL сам по себе не является новым продуктовым решением**.

| Действие страницы | Вход / ожидаемое поведение |
|---|---|
| Показать корты и клиентов | Список семи кортов и клиентов; клиентский телефон доступен сотруднику |
| Показать расписание и доступность | Корт и дата → занятость, сезон, техническое состояние, погодные блоки и предупреждение при неизвестном прогнозе |
| Создать бронь | ID клиента и корта, начало/конец → подтверждение после записи в БД или понятный отказ |
| Перенести бронь | ID брони и новое время → новое состояние или неизменённая старая бронь при отказе |
| Отменить / архивировать | Изменение статуса без физического удаления, запись события истории |
| Перепроверить погоду | Список затронутых открытых броней; сотрудник связывается с клиентом по телефону |
| Подтвердить готовность покрытия | Изменение ручного состояния открытого корта при соблюдении действующего погодного запрета |

Для изменяющих действий сервер проверяет, что сотрудник вошёл в систему, и использует штатную защиту Django от подделки браузерных запросов (CSRF). Неверный ввод не меняет данные; конфликт времени — управляемый ответ, а не авария сервера.

## 8. Что и чем проверяем

Тесты встроенными средствами Django покрывают данные клиентов и обязательный телефон, границы времени, сезонность, соседние интервалы, создание, перенос, отмену, архив и историю, погодную политику, авторизацию и ответы API.

**Главная интеграционная проверка:** два независимых одновременных соединения к **настоящей тестовой PostgreSQL** пытаются занять пересекающееся время одного корта. В результате остаётся ровно одна действующая бронь. Проверку повторяем; SQLite и подставная база не доказывают это свойство PostgreSQL. Для конкурентного сценария тест должен использовать действительно независимые транзакции, а не случайно общий тестовый transaction wrapper.

Для погодных тестов подставляем заранее известные ответы Open-Meteo, чтобы результат не зависел от погоды сегодня. Настоящий сетевой вызов проверяем отдельно после разрешения пользователя. Все выполненные команды, полученные результаты и ограничения доказательства заносим в обязательный `docs/testing-report.md`.

## 9. Источник истины и границы решения

PostgreSQL хранит фактические брони и историю; экран лишь показывает их, а прогноз — внешний входной факт, который может устаревать. Отсутствие прогноза нельзя выдавать за хорошую погоду. Не добавляем Redis/очередь «для надёжности», пока для них нет отдельной проблемы, которую нельзя разумно решить существующими частями.

Целевая схема не означает, что все перечисленные операции уже реализованы. Фактическая граница создания на этапе 05 описана отдельно выше; свидетельства выполненных проверок и оставшиеся ограничения находятся в `docs/testing-report.md`.
