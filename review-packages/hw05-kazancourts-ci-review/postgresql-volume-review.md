# PostgreSQL Debian → Alpine: решение Review

Дата: 14 ноября 2026. Scope: анализ риска и защита конфигурации; перенос рабочих данных не выполнялся.

## Почему нельзя просто сменить tag

Одинаковая версия сервера 18.6 сама по себе не доказывает совместимость физического каталога данных между Debian/glibc и Alpine/musl. Могут отличаться libc/locale/ICU, правила collation, версии библиотек и расширений, UID/GID postgres. Каталог `PGDATA` и major-version могут совпасть, при этом сортировка и соответствующие индексы будут работать иначе. Успешный старт и SELECT 1 этого не выявляют. Init entrypoint может менять владельца файлов, поэтому даже пробное подключение старого тома к новому контейнеру не является безопасной read-only проверкой.

`ALTER COLLATION ... REFRESH VERSION` обновляет метаданные, но само по себе не перестраивает индексы и не доказывает корректность данных. Это не автоматическое решение перехода libc.

## Минимальное решение на этом этапе

1. Для новых локальных/CI-стендов остаётся `postgres:18.6-alpine`, выбранный после аудита слоёв.
2. Compose использует новое имя `compose_postgres_alpine_data`. Старое `compose_postgres_data` не указано в mounts или объявлениях volumes новой конфигурации. В рамках одного project имя нового volume будет `<project>_compose_postgres_alpine_data`.
3. Старый Debian-volume сохраняется. Нельзя переименовывать его, прописывать его имя через external volume override или подключать его к Alpine.
4. Новый volume — пустая отдельная БД. Это не миграция и не доказательство потери старых данных. Если в существующем стенде нужны прежние данные, **не переключать его на новый Compose**, продолжать прежний Debian-стек до отдельного решения о переносе.
5. Не применять `down --volumes` к старому проекту. CI удаляет только собственные заново созданные ресурсы с уникальным префиксом и проверенным ownership marker. Все проверки здесь используют новые тестовые volumes.

Цена: старый и новый стенды используют разные данные. Автоматическое обновление существующего стенда не заявляется. Изменение имени volume предотвращает случайное физическое переиспользование, но не заменяет план миграции.

## Что потребуется отдельно, если перенос данных будет разрешён

Выбрать source/target версии, локали и расширения, зафиксировать downtime и rollback. Выполнить логический dump/restore в новый volume, проверить ограничения, collation/indexes, контрольные данные, API и фоновые сценарии. Исходный Debian-volume сохранить до приёмки. Это только перечень решений для отдельной задачи, **не выполненная практика P11/P12/P13**; готового production-runbook или команды удаления данных здесь нет.

## Доказательства и открытые вопросы

Статическая проверка новой конфигурации и чистый запуск с новым volume выполняются в Codex, с отдельным CI project. Существующие volumes не монтировались и не удалялись.
Фактический Debian→Alpine перенос данных, проверка collation на рабочих данных и GitHub Actions запуск пока **Not Run**.
